# Bookmark Manager GraphQL API

A GraphQL API for organizing bookmarks into folders. Built with Bun, TypeScript, GraphQL Yoga, Prisma, and PostgreSQL.

**Folder → Bookmark relationship:** every bookmark belongs to exactly one folder. Deleting a folder cascades to its bookmarks.

---

## Prerequisites

- [Bun](https://bun.sh) — runtime and package manager
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) — provides PostgreSQL through Docker Compose; no separate PostgreSQL installation needed

---

## Setup

### 1. Clone and enter the repository

```bash
git clone <repository-url>
cd bookmark-manager-graphql
```

### 2. Create the environment file

```bash
# Unix / macOS
cp .env.example .env

# Windows PowerShell
Copy-Item .env.example .env
```

The defaults in `.env.example` match the Docker Compose service exactly, so no edits are needed for local development.

### 3. Start PostgreSQL

```bash
docker compose up -d
```

This starts a PostgreSQL 16 container named `bookmark_manager_db` on port `5432`.

### 4. Install dependencies

```bash
bun install
```

### 5. Apply migrations and generate the Prisma Client

```bash
bun run gendb
```

This runs `prisma migrate dev`, which applies all pending migrations and regenerates the Prisma Client. Run this once on first setup and again after any schema change.

### 6. Start the development server

```bash
bun run dev
```

The GraphQL API is available at `http://localhost:4000/graphql`.

## Database

### PostgreSQL via Docker Compose

PostgreSQL runs as a Docker container defined in `docker-compose.yml`. No external database account or local PostgreSQL installation is required.

```yaml
# docker-compose.yml defaults
POSTGRES_USER: postgres
POSTGRES_PASSWORD: postgres
POSTGRES_DB: bookmark_manager
port: 5432
```

Data is persisted in a named Docker volume (`postgres_data`) so the database survives container restarts.

### Prisma

[Prisma](https://www.prisma.io) is the ORM. The schema is defined in `prisma/schema.prisma`. Migrations live in `prisma/migrations/` and are committed to the repository.

**Do not write SQL migration files by hand.** Migrations are generated by Prisma tooling:

```bash
bun run gendb          # applies pending migrations and regenerates the client
bunx prisma generate   # regenerate the client only (no migration)
```

### Data model

```
Folder
  id        — unique string identifier (cuid)
  name      — folder name
  createdAt — set automatically on creation
  bookmarks — one-to-many → Bookmark

Bookmark
  id        — unique string identifier (cuid)
  title     — bookmark title
  url       — absolute URL
  tags      — array of strings
  folderId  — foreign key → Folder (required, not nullable)
  createdAt — set automatically on creation
```

Deleting a folder cascades to all of its bookmarks (`onDelete: Cascade`).

Indexes:
- `Bookmark.folderId` — supports folder-scoped queries
- `(Bookmark.createdAt, Bookmark.id)` — supports deterministic cursor pagination

## API

### Queries

#### `folders`

Returns all folders, each with their nested bookmarks.

```graphql
query {
  folders {
    id
    name
    createdAt
    bookmarks {
      id
      title
      url
      tags
    }
  }
}
```

---

#### `folder(id: ID!): Folder`

Returns a single folder by ID, including its bookmarks. Returns `null` if the folder does not exist.

```graphql
query {
  folder(id: "clxyz123") {
    id
    name
    bookmarks {
      id
      title
      url
    }
  }
}
```

---

#### `bookmarks(folderId, search, take, cursor): BookmarkPage`

Returns a paginated list of bookmarks with optional filtering.

| Argument | Type | Description |
|---|---|---|
| `folderId` | `ID` | Filter by folder |
| `search` | `String` | Case-insensitive substring match on title |
| `take` | `Int` | Number of items per page (default: 20, max: 100) |
| `cursor` | `String` | Opaque cursor from a previous response |

Returns a `BookmarkPage`:

```graphql
type BookmarkPage {
  items: [Bookmark!]!
  nextCursor: String   # null when there are no more results
}
```

```graphql
query {
  bookmarks(folderId: "clxyz123", search: "docs", take: 10) {
    items {
      id
      title
      url
      tags
      createdAt
    }
    nextCursor
  }
}
```

---

### Mutations

#### `createFolder(input: CreateFolderInput!): Folder!`

Creates a new folder. The name is trimmed and must not be empty.

```graphql
mutation {
  createFolder(input: { name: "Development" }) {
    id
    name
    createdAt
  }
}
```

---

#### `createBookmark(input: CreateBookmarkInput!): Bookmark!`

Creates a bookmark in the specified folder. `tags` defaults to `[]` if omitted.

```graphql
mutation {
  createBookmark(input: {
    title: "Bun Documentation"
    url: "https://bun.sh/docs"
    tags: ["runtime", "javascript"]
    folderId: "clxyz123"
  }) {
    id
    title
    url
    tags
    folderId
    createdAt
  }
}
```

---

#### `updateBookmark(id: ID!, input: UpdateBookmarkInput!): Bookmark!`

Updates a bookmark. Only the fields included in `input` are changed; omitted fields are left unchanged.

```graphql
mutation {
  updateBookmark(
    id: "clbm456"
    input: {
      title: "Bun Runtime Docs"
      tags: ["runtime", "bun"]
    }
  ) {
    id
    title
    url
    tags
  }
}
```

---

#### `deleteBookmark(id: ID!): Boolean!`

Deletes a bookmark. Returns `true` on success.

```graphql
mutation {
  deleteBookmark(id: "clbm456")
}
```

---

#### `moveBookmark(id: ID!, folderId: ID!): Bookmark!`

Moves a bookmark to a different folder. Both the bookmark and the destination folder must exist.

```graphql
mutation {
  moveBookmark(id: "clbm456", folderId: "clxyz789") {
    id
    title
    folderId
  }
}
```

## Pagination

The `bookmarks` query uses **cursor-based pagination**, not offset pagination. This guarantees stable, consistent pages even when records are inserted or deleted between requests.

### How it works

Results are always ordered by `(createdAt ASC, id ASC)`. The composite key is deterministic: if two bookmarks share the same `createdAt` timestamp, the `id` breaks the tie.

The server fetches `take + 1` rows. If the extra row exists, the page has more results and `nextCursor` is returned; otherwise `nextCursor` is `null`.

### Cursor encoding

The cursor is an opaque Base64 string encoding `{ createdAt, id }` of the last item on the current page. Clients should treat it as an opaque token — do not parse or construct it manually.

### Arguments

| Argument | Default | Maximum | Description |
|---|---|---|---|
| `take` | `20` | `100` | Items per page |
| `cursor` | — | — | Pass `nextCursor` from the previous response |

### Example: walking through pages

**Page 1** — no cursor:

```graphql
query {
  bookmarks(take: 2) {
    items { id title }
    nextCursor
  }
}
```

```json
{
  "data": {
    "bookmarks": {
      "items": [
        { "id": "bm-1", "title": "Bun Docs" },
        { "id": "bm-2", "title": "Prisma Docs" }
      ],
      "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI0LTAxLTAyVDAwOjAwOjAwLjAwMFoiLCJpZCI6ImJtLTIifQ=="
    }
  }
}
```

**Page 2** — pass `nextCursor` as `cursor`:

```graphql
query {
  bookmarks(take: 2, cursor: "eyJjcmVhdGVkQXQiOiIyMDI0LTAxLTAyVDAwOjAwOjAwLjAwMFoiLCJpZCI6ImJtLTIifQ==") {
    items { id title }
    nextCursor
  }
}
```

When `nextCursor` is `null`, you have reached the last page.

Filters (`folderId`, `search`) work together with pagination — the cursor continues within the same filtered set across requests.

## Validation and Error Handling

Validation errors and missing-resource errors are returned as standard GraphQL errors with an `extensions.code` field. They do not produce HTTP 500 responses.

### Validation rules

| Field | Rule |
|---|---|
| Folder `name` | Must not be empty or whitespace-only. Surrounding whitespace is trimmed. |
| Bookmark `title` | Must not be empty or whitespace-only. Surrounding whitespace is trimmed. |
| Bookmark `url` | Must be a valid absolute URL using the `http` or `https` protocol. |

### Error codes

| Code | Meaning |
|---|---|
| `BAD_USER_INPUT` | Invalid input — empty name, bad URL, invalid `take`, malformed cursor |
| `NOT_FOUND` | Bookmark or folder does not exist |

### Example error response

```json
{
  "errors": [
    {
      "message": "Bookmark URL must be a valid absolute URL.",
      "path": ["createBookmark"],
      "extensions": { "code": "BAD_USER_INPUT" }
    }
  ],
  "data": null
}
```

### Specific cases handled

- Empty or whitespace-only folder name → `BAD_USER_INPUT`
- Empty or whitespace-only bookmark title → `BAD_USER_INPUT`
- Malformed URL or non-http/https protocol → `BAD_USER_INPUT`
- `folderId` does not refer to an existing folder (on create/move) → `NOT_FOUND`
- Bookmark not found (on update, delete, move) → `NOT_FOUND`
- Invalid `take` value (zero, negative, above 100) → `BAD_USER_INPUT`
- Malformed pagination cursor → `BAD_USER_INPUT`

## Testing

### Run the full test suite

```bash
bun run test
```

PostgreSQL must be running (`docker compose up -d`) for the integration tests to pass.

### Unit tests

Located in `tests/resolvers/`. These test resolver behavior in isolation with a mocked Prisma client. They do not require Docker or a database connection and run quickly.

Covered behaviors include:
- folder and bookmark query logic
- pagination (`take+1` strategy, `nextCursor` presence/absence, cursor where-clause)
- all mutation success paths
- validation error paths (`BAD_USER_INPUT`, `NOT_FOUND`)
- Prisma is not called when validation fails early

### Integration tests

Located in `tests/integration/postgres.test.ts`. These use a real `PrismaClient` connected to the PostgreSQL container — no mocking.

Covered behaviors include:
- folder creation and retrieval
- bookmark creation with correct field values (including tags array)
- Folder → Bookmark relationship via Prisma `include`
- cascade delete (folder deletion removes its bookmarks)
- `folderId` filtering via `findMany`
- case-insensitive title search via `findMany`

Each test creates its own uniquely identifiable records and deletes them in `afterEach`, so the tests are safe to run against a database that already contains data.

### Type checking

```bash
bun run typecheck
```

## Development: Changing the Schema

The normal workflow for a Prisma schema change:

1. Edit `prisma/schema.prisma`
2. Run `bun run gendb` — this creates a migration file and applies it to the database
3. Commit both the updated schema and the generated migration in `prisma/migrations/`
4. Run `bun run typecheck` and `bun run test` to confirm nothing is broken

Do not manually write SQL files as a substitute for running `prisma migrate dev`.

## Troubleshooting

**Docker isn't running**

Start Docker Desktop, then run `docker compose up -d`.

**PostgreSQL container is not running**

```bash
docker compose ps          # check status
docker compose up -d       # start it
docker compose logs postgres   # inspect logs if it fails to start
```

**`DATABASE_URL` is missing or incorrect**

Ensure `.env` exists and contains a valid `DATABASE_URL`. Copy from `.env.example` if needed.

**Prisma Client is out of date**

After pulling changes that include a new migration, run `bun run gendb` to apply migrations and regenerate the client.

**Port 4000 is already in use**

Set a different port in `.env`:

```
PORT=4001
```

Then restart the server with `bun run dev`.

**Integration tests fail with a connection error**

The integration test suite requires the PostgreSQL container to be running. Run `docker compose up -d` before `bun run test`.

## How I'd Extend This

These are directions a production version of this API could evolve. None of them are currently implemented.

**Authentication and authorization**
Add user accounts (e.g., JWT-based auth) so each user has their own folders and bookmarks. Field-level authorization would prevent users from accessing each other's data.

**Improved search**
The current title search uses a simple `ILIKE` substring match. A production system could use PostgreSQL full-text search or an external index (e.g., Elasticsearch, Typesense) for ranking, stemming, and cross-field search (title + URL + tags).

**Caching**
Frequently read queries like `folders` could be cached at the resolver level or behind a CDN/edge layer. DataLoader could be introduced to batch and cache Prisma lookups within a single request, eliminating any N+1 patterns.

**Observability**
Add structured logging (e.g., Pino), request tracing (OpenTelemetry), and metrics (Prometheus) to make the service debuggable in production.

**API versioning**
GraphQL handles many schema changes without versioning (additive changes are non-breaking), but a deprecation strategy for removed or renamed fields would be needed over time.

**Scaling**
The current setup is a single Bun process. Horizontal scaling would require externalizing session state, using a connection pool (e.g., PgBouncer), and deploying behind a load balancer. The stateless resolver architecture already supports this.

**Soft deletes and audit history**
Add `deletedAt` timestamps and a change-log table to support undo/recovery and audit requirements.
